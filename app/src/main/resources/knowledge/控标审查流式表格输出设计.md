# 控标审查流式表格输出设计（待实施）

> 状态：**设计已定稿、未实施**。本文档供后续开发沿用，当前代码（`BidControlReview.review`）
> 已完成"流式过程 + 阻塞收结构化结果"的第一阶段；本文档描述的第二阶段是把最终表格
> 也变成随模型生成逐块流出的 `Flux<String>`，供前端做打字机式表格渲染。

## 一、目标

`BidControlReview.review` 未来返回 `Flux<String>` 给前端：

- 内容为**纯 markdown 表格**（表头 → 逐行 → 免责声明），前端拿到即可当 markdown 渲染；
- 不等整个 JSON 生成完，而是**表格随模型生成逐块增长**；
- 思考/检索进度文本**不混入** Flux（走服务端 stderr 日志或未来单独的 SSE 通道），避免污染表格。

## 二、为什么可行（已确认的框架事实）

AgentScope 2.0.4 中 `agent.stream(msg, options, schema)` 与 `agent.call(msg, schema)`
共用同一条 `doStructuredCall` 管道（generate_response 合成工具收口，见
`ModelConfig.qwen37PlusBidControlReportModel` 中关闭 nativeStructuredOutput 的注释）。
关键事实：**模型流式吐 `generate_response` 工具参数的阶段，参数增量以 ToolUseBlock
形式随 REASONING 事件的每个 chunk 到达**（chunk 的 `Msg.getContentBlocks(ToolUseBlock.class)`
里可取到，此时 `getTextContent()` 为空）。也就是说，行的 JSON 是 token 级流出来的，
服务端完全可以边收边检测"哪一行的 JSON 闭合了"，闭合一行渲染一行。

注意：该增量粒度是从字节码与事件结构推断的，**实施前第一优先级是写探针实测**
（打印 REASONING 事件中 ToolUseBlock 的到达时机与内容），确认是 token 级增量
而非整轮才可见。若实测只有整轮才见完整参数，走备选路径：`streamEvents()`（细粒度
事件，含 `ToolCallDeltaEvent.getDelta()` 参数增量，但不支持 schema 参数）+ 自行向
Toolkit 注册 generate_response 工具 + 出口用 ToolValidator 校验——消费端渲染逻辑
不变，只换事件源。

## 三、三种发射粒度（实施时按前端需要选）

| 粒度 | 触发时机 | 前端效果 | 实现代价 |
|---|---|---|---|
| 行级 | 一行的 JSON 对象闭合 | 每隔几十秒出一行 | 低 |
| 格级 | 每个单元格的值闭合（值字符串引号闭合） | 表格一格一格长出来 | 中（同一状态机，多几个发射点） |
| 字级 | 单元格内容每来一个 token 就透传 | 单元格内容逐字生长，真打字机 | 中高（流式过程中实时转义：`\n`→空格、`\|`→`｜`） |

三级共用同一套底层设施（参数增量提取 + 字符串感知的 JSON 状态机），区别只在
状态机在哪些点位向外发 chunk。倾向格级：代价与鲁棒性平衡最好。

客观约束：markdown 表格语法要求表头+分隔行在最前，这两个 chunk 在第一行数据
开始生成时就发；行未闭合时前端会看到一行缺右边界的半成品，主流 markdown 渲染器
（含各类聊天 UI）都能优雅处理，但前端组件需确认对不完整表格行的兼容性。

## 四、实施要点

1. **参数增量收集**：订阅 `StreamOptions.eventTypes(REASONING, TOOL_RESULT, AGENT_RESULT)`
   （必须显式订阅，否则假流式——见 `BidControlReview` 现有注释），REASONING 事件中
   `getContentBlocks(ToolUseBlock.class)` 的增量追加进 argsBuffer。
2. **字符串感知扫描器**（自写约 50 行，勿引第三方库）：对 argsBuffer 做大括号深度
   扫描，处理引号开合与 `\` 转义（单元格内容含 `{}`、`|`、换行的场景），检测
   `"risks": [ {...}, {...} ]` 中深度 2 的对象闭合点。闭合即得一行完整 JSON。
3. **渲染与校验**：闭合行 → Jackson 反序列化为 `BidControlRiskRow` → 对象级 6 字段
   非空校验（复用 `validateRows` 的单行逻辑）→ `MarkdownTables` 发行 chunk。
   `MarkdownTables` 需增加 `header(Class)` / `row(T)` 两个流式 API（复用现有
   columnOf/escapeCell），`render(List)` 改为基于两者实现。
4. **双保险兜底**：最后一条 `AGENT_RESULT` 事件的 `getStructuredData(BidControlRiskTable.class)`
   拿最终对象，与已发行数比对，补发扫描器漏掉的行；若一个 chunk 都没发过（增量
   不可用），退化为一次性发整表（即现状，不报错）。
5. **错误语义**：单行校验失败 → `sink.error`（前端收到错误而非残缺报告）；
   宁缺毋滥原则不变。
6. **main 与探针适配**：`main` 用 `review(...).doOnNext(System.out::print).blockLast()`；
   `BidControlRagProbe` review 模式收集 chunks 断言表头/免责声明，并断言
   "chunk 数 > 1"以证明真流式。

## 五、历史教训（为什么是现在这个形态）

- 结构化输出与 AGENTIC 检索工具冲突的根因是 native 路径（response_format）在多工具
  循环下收不住 schema；显式 `nativeStructuredOutput(false)+WithTools(false)` 走
  generate_response fallback 后两者共存（qwen3.7-plus/3.8-flash/3.8-max 三模型实测）。
- 粗粒度 stream() 的 REASONING 事件在工具调用轮次文本为空，enableThinking(false)
  下思考增量也没有——"过程可见性"若要加强，可考虑开启 thinking 或按轮次打进度行，
  与本设计的 Flux 表格通道相互独立，不要混流。
- `ImmConcurrentStreamReviewBy38Flash` 的"流式"只订阅了 AGENT_RESULT，实为假流式；
  新代码订阅过程事件时务必显式列全 eventTypes。
